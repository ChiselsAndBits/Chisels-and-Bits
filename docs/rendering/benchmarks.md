# Rendering benchmarks (Phase 0)

This document describes how to generate the baseline test scenes, capture render metrics, and record results. It belongs to Phase 0 of the [PoC plan](07-poc-plan.md).

Scenes are generated by a debug command, so no world is checked in. Commands run on a singleplayer or operator client/server.

## Scenes

Each scene is generated relative to a position. The default is two blocks in front of the player (`x+2`), and you can pass an explicit position.

| Scene | Command | What it exercises |
|---|---|---|
| worst_case | `/candb scene worst_case [pos]` | One 16×16×16 section filled with blocks whose 16³ bits alternate stone/air in a 3D checkerboard. Maximum quad count and mesh cost. |
| sharding | `/candb scene sharding [pos]` | A smaller 5×5×5 cube of the same checkerboard blocks, for experimental opaque sharding acceptance. Place wholly inside one render section. |
| terrain_subset | `/candb scene terrain_subset [pos]` | Two stone shapes: an inset cube and a boundary-touching slab, both eligible for experimental native rectangles. |
| builder_detail | `/candb scene builder_detail [pos]` | About 1000 realistic chiseled blocks (stairs, trims, carvings, mixed materials). Typical builder workload. |
| translucency | `/candb scene translucency [pos]` | Glass, stained glass and water bits next to vanilla water. Translucency sorting and blending. |
| lighting | `/candb scene lighting [pos]` | Inset faces near torches and glowstone bits, under overhangs. Lighting parity. |
| churn | `/candb scene churn [pos] [ticks]` | Re-chisels blocks every server tick for `ticks` ticks (default 200, max 100000). Re-mesh storm. |

Stop a running churn scene with `/candb scene stop`. Scenes are placed on top of existing blocks, so run them in an empty area or clear the region first with `/candb clear`.

For the experimental terrain producer, launch the NeoForge client with
`-PscenaNativeTerrainGeometry=true -PcandbDebugTerrainGeometry=true`, then run
`/candb scene terrain_subset` in a disposable world. The command clears a 5×3×3 area
including a one-block margin, so do not use it near anything you want to keep. The inset
cube is at the reported origin; the boundary-touching slab is two blocks east. Look for
the first `rectangle subset` and `legacy baked model` diagnostic messages in chat or
`neoforge/runs/client/logs/latest.log`. Diagnostics are emitted only once per selection
per client process and do not by themselves establish visual parity.
On NeoForge, also look in the log for `selected native vertex output` to identify the
experimental native-buffer adapter; rectangle selection alone does not prove it ran.

On the first NeoForge in-world run (2026-11-12), the diagnostic reported the legacy path
at the inset cube's position; no rectangle selection was logged. After correcting the
source-model key preflight, a second run reported rectangle selection at the inset cube
and legacy selection at the boundary slab. The user reported that it appeared to work;
this is not an output-level or pixel comparison.

After adding the NeoForge native-buffer adapter, another run reported native vertex
output for the inset cube and legacy selection for the boundary slab; the user reported
both looked correct. Sharding was not enabled in that run.

## Capturing metrics

**Known baseline failure (2026-11-12):** `worst_case` crashes the 26.2 client on
NeoForge 26.2.0.93 during terrain upload:
`Cannot fit allocation of size 379545600 into staging buffer of size 102760448`.
That is approximately 362 MiB for one allocation versus 98 MiB staging capacity.
Record this scene as a failed baseline, not an FPS result. Avoid generating it in a
world you need to keep using: loading the affected area can trigger the crash again.
Server-side scene tests do not exercise this upload path.

Metrics are collected on the client only and written when collection stops.

1. Choose an empty area and position the camera so the scene will be in view.
2. Run `/candb bench start`, then generate the scene to include its initial section compiles. Collection records:
   - section compile time (p50 and p99, in ms) from the vanilla `SectionCompiler` mixin,
   - quads per compiled section (the mixin estimates these from the vertex count, assuming quad topology),
   - FPS samples,
   - chisel-to-visible latency (p50 and p99, in ms) from the start of the model-data update to the main-thread completion callback in `ChiseledBlockModelDataExecutor`. This is an approximation.
3. Perform the workload: let churn run, or chisel blocks manually.
4. Run `/candb bench stop`. The summary is printed in chat and written to `<gameDir>/chiselsandbits-benchmarks/bench-yyyyMMdd-HHmmss.txt`.

`Section compile (ms): no samples` means missing measurements, not zero redraws.
The initial NeoForge hook selected the wrong `compile` overload; it now explicitly
targets NeoForge's five-argument overload (Fabric uses four arguments). Restart the
client after rebuilding to load the updated mixin. For an existing scene, F3+A
while recording triggers terrain rebuilds without generating it again.

Metric collection has no overhead when inactive. The hooks check a flag before recording.

### Optional JFR profiling

For a deeper look, start Java Flight Recorder alongside the bench run, for example:

```
-XX:StartFlightRecording=filename=rendering.jfr,settings=profile
```

Open the `.jfr` file in JDK Mission Control and look at the `SectionCompiler` and `ChiseledBlockModelDataExecutor` frames. `/candb profiling start|stop` is also available for the existing profiler.

### Paired section-compile probe

The disposable world check can also alternate native and baked compilation of the
same section, after five warmup pairs, for 100 measured pairs:

```sh
./gradlew --offline :neoforge:verifyTerrainWorld -PcandbTerrainWorldCheck=true -PcandbTerrainCompileBenchmark=true --no-parallel --max-workers=1
./gradlew --offline :fabric:verifyTerrainWorld -PcandbTerrainWorldCheck=true -PcandbTerrainCompileBenchmark=true --no-parallel --max-workers=1
```

The section contains 27 isolated opaque half-block shapes plus the translucent
boundary fixture. Each sample checks the latter's sorted vertex bytes, then records
the compiler worker's elapsed time and thread allocation before the capture reads
the result. Native samples require all 27 probe blocks to emit natively; baked
samples require none. The baked path uses the already-published model's memoized fallback;
this measures warm section compilation, not initial model generation or GPU upload.
The times below are a single run per loader and sharding setting. Allocations are
bytes per section compile; `-1` means thread allocation accounting is unavailable.

| NeoForge | off | native | 0.471 | 0.780 | 92,360 | 94,152 |
| NeoForge | off | baked | 0.376 | 0.688 | 30,248 | 30,408 |
| NeoForge | on | native | 0.435 | 0.689 | 92,360 | 94,152 |
| NeoForge | on | baked | 0.352 | 0.556 | 30,248 | 30,384 |
| Fabric | off | native | 0.579 | 0.913 | 44,656 | 46,720 |
| Fabric | off | baked | 0.490 | 0.830 | 27,616 | 34,088 |

The native path is slower and allocates more for this small warm fixture, so the
Phase 2 performance exit criterion is not met. Before removing repeated directional
stream grouping, NeoForge's native allocation p50 was 247,944 bytes in the same
probe. These results are not directly comparable to the Phase 0 scene-generation
rows above and do not establish p99 for realistic scenes or forced sharding. Set
`-PscenaTerrainSharding=true` to repeat the sharding-on runs; the fixture itself is
too small to force a shard.

## Automated tests

Scene correctness is checked by NeoForge GameTests (server-side, no renderer). Run them with:

```
./gradlew :neoforge:runGameTestServer
```

The server exits by itself. Exit code 0 means all required tests passed. The tests live in `neoforge/src/main/java/mod/chiselsandbits/forge/gametest/`:

| Test | Asserts |
|------|---------|
| `worst_case` | 4096 chiseled blocks; a sampled block has exactly 2048 non-air bits |
| `sharding` | 125 checkerboard blocks for a smaller in-world sharding check |
| `terrain_subset` | Two blocks containing the intended interior and boundary shapes |
| `builder_detail` | 1000 chiseled blocks in the 10³ cube |
| `translucency` | 8 blocks; glass, stained glass and water bits are present |
| `lighting` | 12 blocks; torch and glowstone bits are present |
| `churn` | 16 blocks; 40 ticks of re-chiseling run without exceptions and the scene changes |
| `mesher_reference_expansion` | Packed rectangles expand to exactly the naive 6-neighbour face set (seeded fills, all sizes, boundaries, transparency) |
| `mesher_legacy_coverage` | Face set equals `GreedyMeshBuilder` where its ANY_OCCUPIED semantics agree |
| `mesher_snapshot_invariants` | Snapshot immutability after source mutation; version, cache and boundary invalidation |
| `mesher_boundary_plane_indexing` | A neighbour in each of the six directions, at each boundary position, hides exactly the expected face and matches the reference |
| `mesher_benchmark` | Opt-in (marker file); runs only when enabled, see "Phase 1 mesher benchmark" |

The scenes are built on an in-memory empty 32³ structure template (`EmptyStructureTemplate`), not a shipped NBT file.

The `registry_serialization` regression test also round-trips every C&B test instance through Minecraft's registry-aware codec, covering serialization needed when clients join.

The test count includes one vanilla `minecraft:default` test that the harness also runs.

Render metrics cannot be captured in a GameTest, because GameTests run server-side without a renderer. They are always captured manually in the client as described above.

### Client-baked model parity

Run `./gradlew :neoforge:verifyTerrainModelParity -PcandbTerrainModelParity=true`.
This starts a bounded client in `neoforge/runs/terrain-model-parity`, checks actual
client-baked models, and exits without opening a world. It compares quad positions,
UVs, culling, material/tint metadata and part AO metadata for an interior stone bit,
stone cuboid, mixed stone/oak shape, full boundary cube and boundary slab. It also checks
one boundary bit in each direction against air, solid, chiseled and edited-neighbour
snapshots at two block positions, retaining one directional and five unculled faces.
Strict output mutation and same-coverage/different-tessellation rejection tests remain.
Glass, water/lava, emissive sea lanterns, animated prismarine and non-cube short grass retain fallback in that earlier slice (see the expanded slice in `03-scena-api.md`).
All passed on NeoForge and Fabric on 2026-11-12. This is not a
pixel, lighting, or general-model parity test.

The same harness runs with `:fabric:verifyTerrainModelParity`. Both offline runs now
also check independently produced metadata against the isolated legacy oracle, no full
legacy build during supported production, memoized fallback identity across threads,
distinct grass/redstone tint table order, nested/exceptional/thread-local scope cleanup,
and table replacement between preflight and emission. Loader-API snapshot views reject
any attempt to read a live block entity; both native rejection and hook-bypass baked
fallback retain coherent colors after replacement and a cache reload.

Run `./gradlew --offline :fabric:verifyTerrainWorld -PcandbTerrainWorldCheck=true`
for a bounded real Indigo-world test. Both scene shapes must publish coherent direct
geometry, survive resource reload and five cold-cache rebuilds, then retain it through
six-direction air/solid/chiseled neighbour changes, neighbour bit edits and an owner
slab edit. The verifier requires separate log evidence that **boundary** native emission
actually ran, not merely that the inset cube emitted. The generated save is removed
only when directly inside the isolated test saves directory and absent before the run;
pre-existing worlds are never deleted.

The static-cutout extension passes both loader parity harnesses with actual oak/spruce/birch
CUTOUT leaves, adjacent stone/leaves and distinct tinted leaves, boundary leaves, leaf cavities,
a stone cavity containing buried leaves, and an occluding grass-block cavity with CUTOUT overlays.
Mixed interfaces retain the ten legacy quads; non-opaque shapes retain cavity faces. Six-direction
neighbour snapshot checks now cover leaves as well as stone. The Fabric world check additionally
compiles a leaf slab, leaf cavity, mixed pair and buried-leaf cavity without constructing a baked
fallback, compares independent legacy output, and requires glass/waterlogged-leaf fallback.
Commands used offline on 2026-11-12:
`./gradlew --offline :fabric:verifyTerrainModelParity :neoforge:verifyTerrainModelParity -PcandbTerrainModelParity=true`,
`./gradlew --offline :fabric:verifyTerrainWorld -PcandbTerrainWorldCheck=true`, and
`./gradlew --offline :neoforge:runGameTestServer` (18 required tests passed).
The original run above did not include a NeoForge disposable-world or pixel comparison.
The world check also passed with `-PscenaTerrainSharding=true`. A real mixed corner/cavity
layout remains a tested legacy fallback because rectangle tessellation differs; acceptance
does not bypass the layout guard. Final NeoForge reruns needed the isolated run's
`config/fml.toml` `earlyWindowControl=false` to avoid an early-splash primary-monitor error;
the original setting was restored afterward.

Existing Scena adapter checks passed unchanged (15 tests), with no publication:

./gradlew -p ../Scena --offline \

  :fabric:test --tests '*ResolvedTerrainModelTest' --tests '*NativeTerrainCompatibilityTest' \
  :neoforge:test --tests '*ResolvedTerrainModelTest' --tests '*NativeTerrainCompatibilityTest'

The direct-snapshot slice also asserts that initial native section compilation builds
neither an eager legacy model nor the lazy baked fallback. It then disables the geometry
hook, dirties the section and requires real Indigo compilation to construct the fallback,
restoring the property in `finally`. Actual resource reload must automatically replace
published model data without the test explicitly requesting a rebuild.
This passed offline with sharding off. It simulates hook bypass, not an installed Sodium
renderer, and does not check pixels.

The boundary producer preserves directional cull groups for normal host occlusion.
For pure fluid and mutually self-culling glass faces against chiseled neighbours, immutable
boundary planes additionally remove matching cells and split partial rectangles. Baked
fallbacks apply the same safe boundary clipping while retaining sealed-cavity faces.
Six-direction neighbour snapshots are captured on the client thread; publication restarts
when the neighbourhood has changed, and payloads and chunk transitions request rebuilds.
The Fabric disposable world checks cross-chunk edits, unload/reload, and mixed native/baked
neighbours, with sharding off and on. Both loader disposable-world checks compare compiled
native and baked translucent vertex buffers and confirm sort indices. Both also check
neighbour chunk unload/reload and mixed native/legacy fluid boundaries where the legacy
block contains an interior glass or non-cubic stair bit, followed by a boundary stair bit,
then is edited back to water. The boundary stair fixture checks that matching water faces
are removed while the stair face and its opposing water face remain. Run the NeoForge check with
`./gradlew --offline :neoforge:verifyTerrainWorld -PcandbTerrainWorldCheck=true`.
Both checks also pass with `-PscenaTerrainSharding=true`; these small fixtures do not force a shard.
In the NeoForge asymmetric-light fixture, the original and split faces differ in interpolated
color and light coordinates, despite matching between native and baked split buffers.
The experimental triangle clipper reproduces the original unquantized vertex-attribute interpolation in this
fixture. Scena's post-light writers are tested but their clipped faces are rejected by both runtime compatibility
guards: the vanilla terrain shader samples a dynamic lightmap per vertex and multiplies it by vertex color, so
attribute interpolation alone is not pixel-equivalent even with a linear lightmap.
Split/unsplit pixel equivalence, vanilla glass/fluid interfaces, and general seams from unsupported
non-affine or non-cubic fallback faces remain unresolved; the stair fixture covers one case only.

`mesher_cavity_faces` preserves the default adjacent-air semantics (a sealed single-bit
pocket still emits six internal unit faces) and separately tests the opt-in sealed-air
API: sealed pocket removed, open and turning one-bit tunnels preserved, and
glass/leaves/water rejected. The supported native producer now enables sealed-air removal;
its lazy baked fallback retains the sealed-cavity faces, subject to safe boundary clipping.

## Phase 1 mesher benchmark (opt-in, server-side)

The Phase 2 producer now copies the packed storage directly from an exact `SimpleSnapshot`
instead of reconstructing it through per-bit accessor objects. Custom accessors and snapshots
with a different configured size are still sampled, but no longer require a temporary packed
storage. Air normalization, custom accessor behavior and snapshot independence are checked
by `mesher_snapshot_invariants`. Neighbour boundaries copy only the touching plane, with
six-direction comparisons against the full-snapshot path.

For a bounded hot-path comparison, run
`JAVA_TOOL_OPTIONS=-Dchiselsandbits.snapshotBenchmark=true ./gradlew --offline :neoforge:runGameTestServer`.
One warmed run on 2026-11-12, using a sparse 16-grid snapshot and 1,000 measured iterations,
reported 389.90 us / 3,476,568 allocated bytes for the old temporary-storage reconstruction,
78.81 us / 338,968 bytes for generic accessor sampling and 44.97 us / 76,600 bytes for the packed
snapshot path. Copying and reading every storage cell separately took 15.94 us / 952 bytes using
the copied storage and 7.01 us / 376 bytes with the packed snapshot, with identical checksums.
Capturing a random neighbour's boundary took 48.36 us / 90,840 bytes through a full snapshot and
6.13 us / 9,264 bytes for the plane-only path. These are microbenchmarks, not section-compile p99
or Phase 2 performance acceptance results.

In a subsequent before/after run, sharing unchanged immutable planes reduced allocation for
capturing all six neighbour planes from 55,432 to 17,992 bytes per operation. The measured
times were 6.26 and 6.30 us respectively; this run does not demonstrate a speedup.

Phase 1 measures the standalone rectangle mesher (`ChiseledRenderSnapshot`, `RectangleMesher`). It runs inside the GameTest server because `BlockInformation` needs Minecraft bootstrap. It is not a client render measurement.

Invocation:

```
mkdir -p neoforge/runs/gameTestServer
touch neoforge/runs/gameTestServer/mesher-benchmark.enabled
./gradlew :neoforge:runGameTestServer
```

The benchmark is gated by `CHISELS_MESHER_BENCHMARK` or the marker file above. Gradle run tasks do not forward the environment variable reliably, so the marker is the working switch. Remove the marker afterwards.

Methodology:
- Equal-work check first. Before timing, each workload asserts that the legacy `GreedyMeshBuilder` expanded unit-face set equals the mesher's expanded set under `FaceCullingPolicy.ANY_OCCUPIED` with an all-air boundary. The log prints `equal_output=true`, plus face and rectangle counts.
- 400 warmup iterations, then 400 timed iterations per operation, in one server JVM, on the server thread. This is a warmed loop, not JMH.
- Each timed operation returns a checksum, a size or a version, and the result is consumed, so the JIT cannot remove the work. Checksums for equal-output operations are logged and match.
- Allocations are `ThreadMXBean` per-thread allocation bytes divided by iterations. They are measured around the timed operation on the server thread. Harness allocations (inputs, timers, log strings) are excluded only as far as the bracket allows, so treat them as approximate.
- Scenarios: `solid`, `checkerboard` (3D, single material), `sparse_3` (3 materials), `multi_material_17` (17 materials).
- Operations:
  - `legacy_greedy_mesh_builder`: `GreedyMeshBuilder` on the same storage. It reads the storage directly and builds its own output.
  - `snapshot_build`: `ChiseledRenderSnapshot.of`, copying the storage into the snapshot. Not cached.
  - `full_snapshot_and_mesh`: `snapshot_build` followed by mesh with `ANY_OCCUPIED` and an all-air boundary. This is the comparable path to legacy, since both start from storage and produce faces.
  - `mesh_uncached_all_air_boundary`: mesh of a prebuilt snapshot, bypassing the intrinsic cache. This is mesh-only cost, not comparable to legacy on its own.
  - `mesh_cached`: intrinsic cache hit on an unchanged snapshot. Cost of a lookup, not a rebuild.
  - `mesh_uncached_opaque_policy_production`: mesh of a prebuilt snapshot with `opaqueOrSameMaterial`. This is the production policy and does different work from legacy (different face set), so it is context only.

Speedup of the comparable path, `legacy / full_snapshot_and_mesh`, per run (run 1 / run 2 / run 3):

| Scenario | run 1 | run 2 | run 3 | Range |
|---|---|---|---|---|
| solid | 4.35× | 3.49× | 3.20× | 3.2–4.4× |
| checkerboard | 4.57× | 4.52× | 4.47× | 4.5× |

Run 3 was executed after the final `ChiseledRenderSnapshot` refactor (helper extraction only, no behaviour change) and matches run 2 within noise. Runs 1 and 2 were executed on the same mesher logic, before that helper extraction.

The planned exit criterion (`07-poc-plan.md`) is at least 5× faster meshing. It is not met on the comparable full path in any run. The best observed ratio is 4.5× (checkerboard, very consistent). The solid case reached 4.35× once and 3.2–3.5× in the other runs.

The mesh-only uncached numbers (for example 15.6 µs solid, 112.7 µs multi) are not a speedup. Legacy does not separate its own snapshot step, so the comparison is not like-for-like.

The production-policy rows (`mesh_uncached_opaque_policy_production`) are different work: for `multi_material_17` the opaque policy gives 4,875 rectangles against 2,505 legacy faces. They are logged, but they are not a speedup claim.

Limits and caveats:
- The legacy builder uses `ANY_OCCUPIED` culling for internal faces but preserves material identity when merging visible faces. The equal-output assertion uses expanded unit faces (coverage plus material). It does not check the merged-face count. `multi_material_17` gives 2,505 legacy merged faces against 2,506 mesher rectangles, which expand to the same 2,664 unit faces.
- The benchmark is a single-threaded warmed loop without JMH. JIT and GC state can differ between runs. The variance above is from three runs only, so it is not a confidence interval.
- `mesh_cached` is an intrinsic cache hit on an unchanged snapshot. It is not a rebuild cost.
- No speedup target was verified, and the 5× criterion is unmet on the comparable path. Phase 1 is not complete on performance.
- Results depend on the machine and on JVM load. Compare only on the same machine.
- Reproduce with the invocation above and read the `MESHER_BENCHMARK` lines in the server log.


## Caveats

- The quads count is an estimate: `vertexCount / 4`, assuming quad topology.
- The chisel-to-visible latency measures to the main-thread callback, not to the frame that displays the change.
- Results vary with hardware, driver and background load. Compare runs on the same machine only.
